# Azure Support Implementation Plan for gopherstack

Findings below are grounded in this repository's own source (paths cited throughout are repo-relative); Azure/Azurite mechanics are standard public documentation.

## 1. How gopherstack is built today (relevant facts)

- **Per-service package layout** (`services/<name>/`): `provider.go` (implements `service.Provider`: `Name()`, `Init(ctx *service.AppContext) (service.Registerable, error)`), `handler.go` (implements `service.Registerable`: `Name()`, `Handler() echo.HandlerFunc`, `RouteMatcher() service.Matcher`, `MatchPriority() int`, `ExtractOperation`/`ExtractResource` for metrics), `store.go` (`InMemoryBackend`), `interfaces.go` (`StorageBackend` interface for testability), `persistence.go` (versioned JSON snapshot/restore), `settings.go`, `janitor.go` (TTL sweeper), `errors.go`, `README.md` + `PARITY.md`. Examples inspected: `services/s3/*`, `services/sqs/*`, `services/dynamodb/*`.
- **Central plumbing** (`pkgs/service/service.go`, `router.go`, `priorities.go`): one Echo HTTP server, one port. Every service registers a `Registerable`; a `Router` sorts all registered matchers by `MatchPriority()` (100=exact header, 95=partial header, 90=form POST, 85=versioned path, 80=standard form, 75=target-prefixed, 50=path UI, 0=catch-all) and evaluates them per request, first match wins. `AppContext{Config, JanitorCtx, Logger, PortAlloc, JanitorTimeout}` is passed to every `Provider.Init`. Optional interfaces a handler can also implement: `DashboardProvider`, `ChaosProvider`, `BackgroundWorker`, `Shutdowner`, `Resettable`, `Purgeable`, `FISActionProvider`.
- **Registration**: new services are added to a flat `[]service.Provider` literal in `cli.go` (`getCoreServiceProviders`/`getRemainingServiceProviders`).
- **Auth**: `services/s3/sigv4.go` shows the house style — SigV4/SigV2 `Authorization` headers are *structurally* parsed and validated, but cryptographic signature verification is opt-in (`WithPresignValidation`/`PresignSecret`); with no secret configured, any credentials are accepted. This is functionally identical to Azurite's fixed-dev-key model, which derisks the whole Azure effort.
- **Persistence**: versioned snapshot structs (`backendSnapshot{Version int, ...}`) restored on boot, guarded against shape drift.
- **Docs/parity machinery**: each service ships a `PARITY.md` (per-op table: `wire`/`errors`/`state`/`persist` status, known gaps, deferred items, audited against a pinned SDK module version) that `cmd/gendocs` renders into the service `README.md` and the root `README.md` services table/badges.
- **Testing conventions**: table-driven unit tests colocated with source, `export_test.go` for whitebox access, `leak_test.go`/`leak_main_test.go` (goroutine-leak checks), `bench_test.go`. `test/integration/<service>_test.go` uses the real upstream AWS SDK (`aws-sdk-go-v2`) against a running instance (via testcontainers), doing full lifecycle flows (e.g. `TestIntegration_SQS_QueueLifecycle`: create → list → get-attrs → delete → verify-gone). No non-Go-SDK wire tests currently exist in the repo.

## 2. Azure wire-protocol minimums (Azurite-equivalent)

**Azurite's dev-auth model** (the shape to copy): a fixed well-known account, `devstoreaccount1`, with a fixed published key (`Eby8vdM02xNOcqFlqUwJPLlmEtlCDXJ1OUzFT50uSRZ6IFsuFq2UVErCz4I6tq/K1SZFPTOtr/KBHBeksoGMGw==`), reachable via `UseDevelopmentStorage=true` or an explicit connection string (`AccountName=devstoreaccount1;AccountKey=...;BlobEndpoint=http://127.0.0.1:10000/devstoreaccount1;QueueEndpoint=http://127.0.0.1:10001/devstoreaccount1;TableEndpoint=http://127.0.0.1:10002/devstoreaccount1`). SDKs sign requests with SharedKey (HMAC-SHA256 over a canonicalized string, key is the base64-decoded account key) into `Authorization: SharedKey devstoreaccount1:<sig>`. Critically, **Azurite runs Blob/Queue/Table on three separate ports (10000/10001/10002)** rather than multiplexing one port — because the path shape (`/<account>/<resource>`) is otherwise ambiguous across the three services.

**Blob** (REST+XML, `x-ms-version` header): `GET /<account>?comp=list` (list containers); `PUT`/`DELETE /<account>/<container>?restype=container` (create/delete container); `PUT /<account>/<container>/<blob>` with `x-ms-blob-type` (put blob), `GET`/`HEAD` (get blob/properties, Range support), `DELETE` (delete blob), `GET /<account>/<container>?restype=container&comp=list` (list blobs). Large-object upload uses Put Block + Put Block List — deferrable to a later pass.

**Queue** (REST+XML): `GET /<account>?comp=list`; `PUT`/`DELETE /<account>/<queue>`; message ops under `/<account>/<queue>/messages`: `POST` (put), `GET` (get, with `numofmessages`/`visibilitytimeout`), `GET ?peekonly=true` (peek), `DELETE /messages/<id>?popreceipt=` (delete), `PUT` (update visibility), `DELETE /messages` (clear).

**Table** (REST+JSON/OData, `Accept: application/json;odata=nometadata`): `POST /<account>/Tables` (create), `DELETE /<account>/Tables('<name>')`, `GET /<account>/Tables` (list); entities: `POST /<account>/<table>` (insert), `PUT`/`MERGE` to `/<account>/<table>(PartitionKey='..',RowKey='..')` (replace/merge, `If-Match` for optimistic concurrency), `DELETE` same path, `GET /<account>/<table>()?$filter=...` (query). Batch (`POST /<account>/$batch`, multipart/mixed changesets) is real-world-important but complex — good candidate for a later milestone. **Important reuse fact: Cosmos DB's Table API is the same wire protocol as Azure Table Storage** (same OData entity model, different auth/endpoint), so Table Storage work is directly reusable for a future Cosmos Table API surface.

**Cosmos DB (Core/SQL API)** is REST+JSON over HTTPS (not just the gRPC/TCP "direct mode" some SDKs also support — the Gateway/REST mode is what unmodified SDKs fall back to and is what's feasible to emulate). Resource hierarchy: `/dbs` → `/dbs/<db>/colls` → `/dbs/<db>/colls/<coll>/docs`. Auth header: `Authorization: type=master&ver=1.0&sig=<base64 HMAC-SHA256>` (URL-encoded), signed with the base64 master key over verb+resourceType+resourceId+date; plus `x-ms-date` and `x-ms-version` headers, and `x-ms-documentdb-partitionkey` on point ops. **The real Cosmos DB Local Emulator uses a fixed, publicly documented well-known master key** (`C2y6yDjf5/R+ob0N8A7Cgv30VRDJIWEHLM+4QDU5DE2nQ9nDuVTqobD4b8mGGyPMbIZnqyMsEcaGQy67XIw/Jw==`) at a fixed endpoint (`https://localhost:8081` for the real emulator) — exactly the same "one fixed dev secret" pattern as Azurite, reinforcing that gopherstack's existing permissive-by-default auth model is the right target here too. Queries execute via `POST .../docs` with `x-ms-documentdb-isquery: True` and a `{"query": "...", "parameters": [...]}` body — needs a small SQL-like query engine, structurally similar to work gopherstack has already done (S3 Select has a full SQL tokenizer/parser/executor in `services/s3/select_sql_*.go`; DynamoDB has its own expression engine in `services/dynamodb/expr/`). Real SDKs also expect `x-ms-request-charge`, `x-ms-session-token`, and `etag` on responses — MVP can return static/fake values rather than real RU accounting.

**Prior art**: an existing open-source lightweight Cosmos DB emulator, **cosmium** (github.com/pikami/cosmium), is worth reviewing directly when scoping the Cosmos milestone (M3) — it has already solved the "how minimal can this REST surface be and still satisfy real SDKs" problem for Cosmos specifically, and is a useful reference for the resource model, the SQL-query subset, and the fake RU/session-token response shape.

## 4. Routing/port strategy (the one real architectural decision)

gopherstack's flagship pattern is single-port, priority-matcher multiplexing — but that only works because AWS services are disambiguated by headers (`X-Amz-Target`) or distinctive path/form shapes. Azure Blob/Queue/Table share the *same* `/<account>/<resource>` path shape with no service-identifying header, so multiplexing them on one port risks exactly the collision the AWS router avoids by construction.

**Recommendation: give each Azure service its own port, mirroring Azurite's own 10000/10001/10002 convention (and Cosmos its own port, mirroring the real emulator's fixed 8081 default).** This is *more* wire-compatible, not less, since SDKs' default connection strings/emulator constants already assume separate ports. gopherstack already has the machinery for this — `AppContext.PortAlloc *portalloc.Allocator` is used elsewhere (e.g. EC2-docker SSH port ranges) for per-resource port allocation, so per-service dedicated listeners are an established pattern, not a new one. Each Azure service's `Provider.Init` stands up its own `echo.Echo` (or shares Echo's engine but binds a second listener), independent of the AWS `Router`.

**On the specific port-selection mechanism (raised in M0 review):** the right model to copy here isn't Azurite's own multi-port convention (10000/10001/10002) or an arbitrary "main port + 1" scheme — it's gopherstack's own existing precedent for a service with a fixed, protocol-conventional port: `services/iot`'s MQTT broker (`services/iot/broker.go`), which hardcodes MQTT's real default (`1883`) and, if that bind fails, simply fails fast rather than silently picking a different port. Azure Blob follows the same pattern: `Settings.Port` (default `10000`, Azurite's own Blob port, overridable via `--azure-blob-port`/`AZURE_BLOB_PORT`) is bound synchronously in `StartWorker`, with **no** fallback into the shared `--port-range-start`/`--port-range-end` `PortAlloc` pool that other resources (Lambda function URLs, ElastiCache) draw ephemeral ports from. A silent fallback would be just as surprising as inventing a different default number: either way, an SDK relying on the well-known default (`UseDevelopmentStorage=true`-style config, with zero further configuration) would end up silently talking to the wrong port. Failing fast with a clear "port already in use" error is simpler and matches the repo's own MQTT precedent.

That said, MQTT's fixed port (`1883`) happens to fall *outside* `--port-range-start`/`--port-range-end`'s own default range (`10000`-`10100`), so it never needed to coordinate with `PortAlloc` at all. Azure Blob's default (`10000`) does **not** have that luck — it sits at the very start of that range. `PortAlloc` only tracks ports it has itself handed out via `Acquire`; it has no way to know Azure Blob bound `10000` directly, and would happily hand that same number to an unrelated `Acquire` caller (e.g. an ElastiCache instance), which would only surface later as a confusing address-in-use failure when that caller tried to actually bind it. `cli.go`'s `reserveFixedServicePorts` closes this gap explicitly: right after the pool is constructed, it calls the new `portalloc.Allocator.Reserve(port, label)` for Azure Blob's configured port, permanently marking it unavailable to `Acquire` (a no-op if the port falls outside the pool's range, exactly MQTT's case). So there *is* coordination between the two, just one-directional and one-time at startup — Azure Blob doesn't ask the pool for anything, but the pool is told to leave Azure Blob's port alone.

## 5. Auth/connection-string strategy per service

- **Blob/Queue/Table**: default to the fixed Azurite account name/key pair (`devstoreaccount1` / the published emulator key) so `UseDevelopmentStorage=true` and unmodified Azurite-targeting SDK config work out of the box. `Authorization: SharedKey ...` headers are parsed structurally (account name extraction for routing/logging); cryptographic verification is opt-in via a `WithSharedKeyValidation` toggle — directly mirroring `services/s3`'s `PresignSecret`/`WithPresignValidation` opt-in pattern. Env var overrides (`AZURE_STORAGE_ACCOUNT`, `AZURE_STORAGE_KEY`) for anyone who wants a non-default identity.
- **Cosmos**: default to the real emulator's published fixed master key at a configurable local endpoint; `Authorization: type=master&ver=1.0&sig=...` parsed structurally, verification opt-in the same way.
- **TLS**: Cosmos SDKs often default to HTTPS even against local emulators, requiring an explicit "allow insecure/disable SSL verification" client flag pointed at plain HTTP — document that flag first (matches gopherstack's lightweight, no-extra-infra ethos); a self-signed cert on the Cosmos listener is a stretch goal, not MVP.

## 6. Implementation order and rationale

1. **Azure Blob Storage** — closest analog to S3 (gopherstack's most mature service); reuses S3's XML serialization, chunked-upload, conditional-header, checksum, and persistence-snapshot patterns almost directly. Lowest risk, highest day-to-day dev-workflow value, fastest to land.
2. **Azure Queue Storage** — also REST+XML (reuses Blob's XML plumbing), and its message lifecycle (visibility timeout, pop receipts) maps closely onto concepts gopherstack already solved for SQS.
3. **Azure Table Storage** — introduces the OData/JSON entity model and a `$filter` mini-grammar; partition-key/row-key semantics map onto DynamoDB's hash/range-key model, so the `services/dynamodb/expr` experience transfers directly to the `$filter` parser.
4. **Cosmos DB (Core/SQL API)** — most complex: master-key HMAC auth, partition-key routing, and a real SQL-like query subset (`SELECT * FROM c WHERE ...`), best tackled last so it can borrow the SQL-parsing muscle built for S3 Select and the entity/query plumbing built for Table Storage (Cosmos's own Table API is literally the Table Storage protocol, a natural stretch goal once both exist). Cross-check scope against cosmium's existing implementation before locking the op list.

## 7. Testing strategy (matches repo conventions)

- **Unit**: table-driven Go tests colocated per file, `t.Parallel()`, `t.Context()`, `export_test.go` for whitebox internals, `leak_test.go`/`leak_main_test.go` for janitor goroutine hygiene, `bench_test.go` for hot paths (blob PUT/GET, table query).
- **Integration** (`test/integration/azureblob_test.go`, `azurequeue_test.go`, `azuretable_test.go`, `cosmosdb_test.go`): use the real `azure-sdk-for-go` client against a running instance via testcontainers, exercising full CRUD lifecycles exactly like `TestIntegration_SQS_QueueLifecycle` (create → list → operate → delete → verify-gone).
- **Cross-SDK wire-compat smoke tests** (the one genuine gap versus existing conventions, since the repo's own suite is Go-SDK-only, but this task's hard requirement is multi-SDK compatibility): add minimal fixtures under the existing `test/e2e/` directory — a short Node script using `@azure/storage-blob`/`@azure/data-tables`/`@azure/cosmos` and a short Python script using `azure-storage-blob`/`azure-cosmos`, run in CI against a live gopherstack instance, proving JS/Python SDKs work unmodified (not just the Go SDK).
- **PARITY.md** seeded per service from day one in the established format (per-op `wire`/`errors`/`state`/`persist` status, known gaps, deferred items, audited against a pinned SDK module version per language — pick `azure-sdk-for-go` as the canonical pinned version for the audit), wired into `cmd/gendocs` so it flows into the service `README.md` and the root README's services table/badges like every existing service.

Cosmos's Table API uses its own independent `*odatatable.InMemoryBackend` instance (`Handler.TableBackend`), disjoint from Core/SQL's database/container/document state, and reuses Cosmos's existing master-key HMAC auth unchanged -- no new auth code, Table-shaped paths just flow through the same `checkAuth` as Core/SQL. `$batch` changesets remain deferred, matching Table Storage's own M2 deferral. Tested via `test/integration/cosmosdb_tableapi_test.go`, which points an unmodified `azure-sdk-for-go/sdk/data/aztables` client at the Cosmos endpoint instead of Table Storage's and runs the same lifecycle assertions as `azuretable_test.go`; `pkgs/odatatable` also has its own standalone unit test suite exercising the engine independent of either caller's wire protocol. `services/cosmosdb/PARITY.md` carries a Table API addendum cross-referencing `services/azuretable/PARITY.md` for the shared engine's known gaps rather than duplicating that list; the one Table-API-integration-specific gap (not an engine gap) is that `TableBackend` isn't yet wired into `Handler.Snapshot`/`Restore`, so Table API state doesn't yet survive a snapshot/restore cycle.

## 9. Next milestones (M13-M14): rounding out the Azure surface

*(Renumbering note, same spirit as section 8's: this section originally numbered its two entries M7 (Key Vault) and M8 (App Configuration). Section 10 below scopes full ARM (Azure Resource Manager) emulation as new milestones, M7-M12, inserted **before** Key Vault/App Configuration -- both of those services' Terraform resources are themselves ARM resources, so building ARM first lets Key Vault and App Configuration each ship their data plane and their ARM resource-provider support in one milestone instead of a retrofit pass later. Key Vault and App Configuration are renumbered M13 and M14 accordingly; see section 10.10 for the full M7-M12 list, including M8's later addition once section 10.8's direct-data-plane finding resolved.)*

These four were chosen by weighing the same three factors gopherstack's existing 160+ AWS services and Azure M0-M3 plan already select for: **dev-workflow value** (would a local developer actually reach for this instead of a live subscription?), **wire-protocol feasibility** (REST-ish, no required real-network fan-out, no heavy sidecar infra), and **pattern reuse** (does it slot into `pkgs/azureauth`, the `services/<name>/` skeleton, and gopherstack's existing AWS analogs — `secretsmanager`/`kms`, `appconfig`/`ssm`, `sns`/`sqs`). Candidates considered and set aside: **Event Grid/Event Hubs** (push-delivery fan-out to external subscriber endpoints and/or a Kafka-compatible streaming wire protocol are a materially different shape of work than anything gopherstack's Azure services do today — better revisited once eventbridge-style patterns are surveyed specifically for Azure, not bundled in here); **Azure Functions** (local trigger emulation is an order of magnitude bigger scope than a storage/config API — even an HTTP-trigger-only stub mostly just reimplements a generic reverse proxy and doesn't teach anything new); **Service Fabric/Container Apps** (infra orchestration, not an emulable data-plane API — no clean in-memory-backend story); **Notification Hubs/SignalR/Communication Services** (niche, low day-to-day dev-workflow pull compared to the alternatives, and SignalR in particular implies a persistent-connection/WebSocket wire protocol gopherstack hasn't needed for any Azure service yet).

### M5 — Azure Service Bus (`services/azureservicebus`)

**Rationale**: Service Bus is Queue Storage's more feature-rich cousin (topics/subscriptions, sessions, dead-lettering) and is one of the highest-value additions for local dev/test workflows -- it's the default choice for real-world pub/sub and worker-queue architectures on Azure, well above Storage Queues in production usage. The full product also speaks AMQP 1.0, which would be a new wire protocol for this repo, but Service Bus additionally exposes a **Brokered Messaging REST API** (`Authorization: SharedAccessSignature ...`, HTTP send/receive/peek-lock/complete/abandon) that covers queues and topics/subscriptions without requiring an AMQP stack -- this REST surface is the MVP target, keeping the wire-protocol lift close to Queue Storage's rather than introducing binary AMQP framing. Complexity is real but bounded: sessions and full AMQP compatibility are explicitly deferred.

- **Package layout**: `services/azureservicebus/` follows the standard skeleton (`provider.go`, `handler.go`, `store.go`, `interfaces.go`, `persistence.go`, `settings.go`, `janitor.go`, `errors.go`, `README.md`, `PARITY.md`) plus `queue_ops.go`, `topic_ops.go`, `subscription_ops.go`, `message_ops.go` (send/peek-lock/complete/abandon/dead-letter), `sas.go`. Message lock/dead-letter semantics reuse the pop-receipt/visibility-timeout pattern already built for `services/azurequeue` (a lock token standing in for a pop receipt); topics/subscriptions reuse gopherstack's existing SNS-topic/SQS-subscription fan-out bookkeeping in `services/sns` as a structural reference for one-to-many delivery without needing real network push (subscribers pull via their own subscription's message endpoint, matching real Service Bus behavior -- no gopherstack-initiated network calls required).
- **Wire-protocol scope**: `PUT`/`DELETE /<queue>?api-version=...` and `/<topic>` (create/delete queue or topic); `PUT`/`DELETE /<topic>/subscriptions/<name>` (subscription CRUD, with an optional SQL-filter rule in the request body -- MVP treats all rules as match-all and defers filter evaluation); `POST /<queue-or-topic>/messages` (send, `BrokerProperties` header carries metadata); `POST /<queue-or-topic-subscription>/messages/head` (peek-lock, destructive read with a lock timeout returning `BrokerProperties.LockToken`); `DELETE /<queue-or-topic-subscription>/messages/<id>/<locktoken>` (complete); `PUT` same path (abandon/unlock); dead-letter sub-queue addressed as `/<queue>/$DeadLetterQueue/messages/head`. Sessions and AMQP are out of scope for the MVP.
- **Auth strategy**: SAS tokens (`Authorization: SharedAccessSignature sr=<resource>&sig=<hmac>&se=<expiry>&skn=<keyname>`, HMAC-SHA256 over the URL-encoded resource string and expiry) are structurally parsed for the key name and resource scope; cryptographic verification is opt-in via a `WithSASValidation` toggle, mirroring `services/s3`'s `WithPresignValidation` and Blob/Queue/Table's `WithSharedKeyValidation`. A fixed default namespace name and root shared-access key (analogous to `devstoreaccount1`) ship so `azure-sdk-for-go`'s default connection-string shape works unmodified.
- **Port-reservation note**: own fixed port, `DefaultPort = 10003` (first available slot after Table's 10002 in gopherstack's own port-numbering convention -- Azurite has no Service Bus emulator to mirror, so this is gopherstack's own choice), synchronous bind, fail-fast, no `PortAlloc` fallback -- identical pattern to Blob/Queue/Table (section 4), registered via the same `reserveFixedServicePorts`/`portalloc.Allocator.Reserve` call in `cli.go`.
- **Testing strategy**: table-driven unit tests plus `leak_test.go` for the dead-letter/lock-expiry janitor; `test/integration/azureservicebus_test.go` against `azure-sdk-for-go`'s `azservicebus` package doing a full send -> peek-lock -> complete lifecycle and a topic/subscription fan-out test; `PARITY.md` seeded day one per the established per-op format.

### M13 — Azure Key Vault (`services/azurekeyvault`)

**Rationale**: Key Vault (secrets/keys/certificates) is likely the single highest dev-workflow-value item left unaddressed -- it's the analog of gopherstack's existing `secretsmanager` and `kms` (both already implemented for AWS), and "load a secret from Key Vault at local-dev time without touching a real Azure subscription" is a very common ask. Scope is deliberately narrowed to **Secrets** as the MVP (matching `secretsmanager`'s scope) with a minimal **Keys** stub for wrap/unwrap-style testing (matching a thin slice of `kms`); full Certificates support and HSM-backed key operations are deferred as a stretch goal, kept out of the MVP the same way Blob's own deferred-gaps list (section 8, M0) kept large-object multipart semantics out of its MVP.
- **Package layout**: standard skeleton plus `secret_ops.go` (set/get/delete/list/versions/recover soft-deleted), `key_ops.go` (create/get/list, wrap/unwrap and sign/verify as thin stubs), `auth.go` (dev-mode bearer-token issuance/validation). Directly modeled on `services/secretsmanager`'s `handler_secrets.go`/`handler_secret_versions.go` split and `services/kms`'s `handler_crypto.go` for the Keys stub's shape.
- **Wire-protocol scope**: REST+JSON, `PUT /secrets/<name>?api-version=7.x` (set, body `{"value": "..."}`), `GET /secrets/<name>/<version>` and `GET /secrets/<name>` (get latest), `GET /secrets` (list, paginated via `nextLink`), `DELETE /secrets/<name>` (soft delete, matching real Key Vault's default soft-delete-enabled behavior so client SDKs' delete/purge/recover flows work unmodified), `GET /deletedsecrets/<name>` and `POST /deletedsecrets/<name>/recover`. Keys: `POST /keys/<name>/create`, `GET /keys/<name>/<version>`, `POST /keys/<name>/<version>/wrapkey` and `/unwrapkey` (stub: reversible XOR/AES-GCM with an in-memory key, not real HSM-backed crypto -- explicitly documented as a testing convenience, not a security boundary, in `PARITY.md`).
- **Auth strategy**: real Key Vault uses Azure AD OAuth2 (`Authorization: Bearer <JWT>`, discovered via a `WWW-Authenticate: Bearer authorization="...", resource="https://vault.azure.net"` challenge on the first unauthenticated request). gopherstack doesn't have a real AAD to talk to, so `services/azurekeyvault` mints structurally-valid, unsigned-or-fixed-secret-signed JWTs from a local dev-token endpoint and accepts any bearer token by default -- directly modeled on `services/cognitoidp`'s existing token-issuing pattern (`auth_tokens.go`), which already solves "emulate an OAuth2 identity provider's token shape without real cryptographic trust" for AWS Cognito. Cryptographic JWT-signature verification is opt-in, consistent with every other Azure service's `With*Validation` toggle.
- **Port-reservation note**: own fixed port, `DefaultPort = 10004`, synchronous bind, fail-fast, no `PortAlloc` fallback, registered via `reserveFixedServicePorts` -- same convention as every other fixed-port Azure service in this plan.
- **Testing strategy**: unit tests for soft-delete/recover/purge lifecycle and the wrap/unwrap stub's round-trip correctness; `test/integration/azurekeyvault_test.go` against `azure-sdk-for-go/sdk/keyvault/azsecrets` (and a minimal `azkeys` smoke test) doing set -> get -> list -> delete -> recover -> purge; `PARITY.md` explicitly flags the Keys stub's non-cryptographic-strength status as a known/permanent gap rather than a deferred TODO.

### M14 — Azure App Configuration (`services/azureappconfig`)

**Rationale**: App Configuration is Azure's key-value/feature-flag config store, directly analogous to gopherstack's existing AWS `appconfig`/`ssm` (both already implemented) -- rounding out config-management parity across clouds the same way Blob/Queue/Table rounded out storage parity. It's simpler than Key Vault or Service Bus (no soft-delete lifecycle, no lock/session semantics) and reuses the `azureauth`-style fixed-secret HMAC auth pattern directly, making it a good "polish" milestone to close out this phase of the plan.
- **Package layout**: standard skeleton plus `kv_ops.go` (key-value CRUD/list/filter by key+label), `featureflag_ops.go` (feature flags are just key-value pairs under the reserved `.appconfig.featureflag/<name>` key prefix with a fixed JSON value schema -- no separate wire surface needed, just a value-shape convention), `revisions.go` (history, can start as a thin read-only projection over the same in-memory store rather than true point-in-time snapshots).
- **Wire-protocol scope**: REST+JSON, `GET /kv?key=<filter>&label=<filter>&api-version=...` (list, `*` wildcard filters), `GET /kv/<key>?label=<label>` (get one), `PUT /kv/<key>` (set, body `{"value": "...", "content_type": "..."}`), `DELETE /kv/<key>` (delete), `If-Match`/ETag-based optimistic concurrency on writes (reusing the same conditional-header handling pattern already built for Blob's and Table's own deferred/implemented conditional-header work). `GET /revisions?key=...` for history is a stretch item, not MVP-blocking.
- **Auth strategy**: real App Configuration uses an `Authorization: HMAC-SHA256 Credential=<id>&SignedHeaders=<headers>&Signature=<sig>` scheme -- a fixed-shared-secret HMAC canonicalization scheme structurally parallel to Blob/Queue/Table's SharedKey (same "one fixed dev credential, opt-in crypto verification" shape), so this becomes a new `pkgs/azureauth`-adjacent canonicalizer (either a new file in `pkgs/azureauth/` if the canonicalization string format is close enough to reuse `canonical.go`'s helpers, or a small sibling package if App Configuration's exact header-signing set diverges too much) rather than a from-scratch auth implementation. A fixed default connection-string credential/secret pair ships for out-of-the-box `az appconfig`/SDK use.
- **Port-reservation note**: own fixed port, `DefaultPort = 10005`, synchronous bind, fail-fast, no `PortAlloc` fallback, registered via `reserveFixedServicePorts` -- same convention as every other service in this plan.
- **Testing strategy**: unit tests for the feature-flag JSON-schema round-trip and ETag concurrency; `test/integration/azureappconfig_test.go` against `azure-sdk-for-go/sdk/data/azappconfig` doing set -> get -> list-by-filter -> delete, plus a feature-flag-specific round-trip test; `PARITY.md` seeded day one, same format as every other service.

## 10. Full ARM (Azure Resource Manager) emulation

*(Grounded in this repository's own source; ARM/AAD wire mechanics are standard public documentation, and the two places where I could not verify a claim from the repo or from primary docs are called out explicitly as pre-implementation spikes in section 10.8.)*

Every AWS service in gopherstack is reachable from unmodified `hashicorp/aws` Terraform today (`test/terraform/terraform_test.go`, ~7.2k lines, plus `test/terraform/*/main.tf` fixtures), because AWS merges control-plane and data-plane onto one per-service endpoint — `CreateBucket` and `PutObject` are both "S3". Azure does not: `terraform-provider-azurerm` provisions essentially everything through **Azure Resource Manager**, a single `management.azure.com` host namespaced by resource provider (`Microsoft.Storage`, `Microsoft.ServiceBus`, `Microsoft.DocumentDB`, `Microsoft.KeyVault`, `Microsoft.AppConfiguration`), authenticated with Azure AD OAuth2 bearer tokens, and only *then* talks to the per-service data-plane endpoints that M0-M6 already emulate. Before M7, gopherstack had zero ARM surface (`grep -rn "management.azure.com\|ResourceManager\|metadata_host"` returned nothing), so `terraform apply` with the real `azurerm` provider failed at the first resource — before it ever reached the working Blob/Queue/Table/Service Bus/Cosmos listeners. This section scopes the ARM emulation that closed that gap for every Azure service already built (M7, done), and that M9/M10 then extend by adding one resource provider each, and M13/M14 by two more, rather than by inventing new plumbing.

### Was deferring ARM until after M0-M6 the wrong call?

**No — the data-plane-first ordering was correct, and building ARM first would have been the worse bet.** ARM is a pure control-plane façade with almost no interesting state of its own: nearly every resource it "creates" is only useful because there is a real data-plane backend behind it (a `Microsoft.ServiceBus/namespaces/queues` resource that can't actually receive a message is a stub, not an emulator), so an ARM-first M0 would have had nothing to delegate to and no way to prove itself against real SDKs — exactly the risk M0-M6 retired by testing against unmodified `azure-sdk-for-go`/JS/Python clients. The build order also produced the reusable machinery ARM now leans on: `pkgs/azureauth`'s fixed-dev-credential model, `pkgs/odatatable`'s extraction precedent (M6), the fixed-port/`reserveFixedServicePorts` convention (section 4), and `services/cosmosdb/account_ops.go`'s hard-won "advertise the endpoint the client actually reached you on" lesson. The one real cost of the ordering is section 10.4's retrofit: M0-M6 all hardcode a single identity (`devstoreaccount1`, `sbemulatorns`, one Cosmos account) and discard the account segment entirely (`services/azureblob/handler.go`'s `splitPath` returns the account and every caller drops it with `_`), so multi-account naming has to be added afterwards instead of designed in — a modest, well-contained cost, not a reason to have inverted the sequence.

### 10.1 What of ARM's surface is actually load-bearing (MVP scope)

ARM's published surface is enormous (management locks, policy, RBAC, deployments/templates, tags as a first-class sub-resource, `Microsoft.Resources/deploymentScripts`, resource-graph queries, per-resource-type API-version negotiation, LRO polling). Almost none of it is on `azurerm`'s critical path for basic CRUD. The MVP is the following, and everything else is an explicit deferral in `PARITY.md` the same way M0 deferred Put Block/Put Block List:

**Discovery and identity (mandatory — the provider will not initialize without these):**
- `GET /metadata/endpoints?api-version=2022-09-01` — the cloud-environment discovery document `metadata_host` points at. Returns a JSON array of environment descriptors; the fields that matter are `name` (must equal the provider's `environment` value), `authentication.loginEndpoint`/`audiences`/`tenant`, `resourceManager`, `gallery`, `graph`/`graphAudience` (real ARM rejects pre-2019-05-01-shaped metadata for lacking this — include it even though it isn't otherwise used), `portal`, and `suffixes.{storage,keyVaultDns,sqlServerHostname,acrLoginServer}`. Every one of those URLs points back at gopherstack. This single document is what makes the whole scheme work, and it is the first thing to build.
- `GET /{tenant}/v2.0/.well-known/openid-configuration` and `GET /common/discovery/instance?api-version=1.1` — AAD instance/authority discovery, which `azidentity`/`go-azure-sdk` perform against `loginEndpoint` before requesting a token. Implement both rather than relying on a provider-side `disable_instance_discovery` toggle.
- `POST /{tenant}/oauth2/v2.0/token` (and the v1 `/{tenant}/oauth2/token` shape) — client-credentials grant, form-encoded `grant_type=client_credentials&client_id=&client_secret=&scope=https://management.azure.com/.default`, returning `{"token_type":"Bearer","expires_in":3599,"access_token":"<JWT>"}`.
- `GET /subscriptions/{sub}?api-version=2022-12-01` and `GET /subscriptions`, `GET /tenants` — azurerm 4.x validates the configured `subscription_id` on startup.

**Generic ARM resource plane:**
- `PUT`/`GET`/`DELETE /subscriptions/{sub}/resourcegroups/{name}?api-version=2021-04-01` (case-insensitively — real ARM accepts `resourcegroups` and `resourceGroups` interchangeably and azurerm emits both; normalize on the way in).
- `PUT`/`GET`/`DELETE /subscriptions/{sub}/resourceGroups/{rg}/providers/{namespace}/{type}/{name}[/{subtype}/{subname}...]?api-version=...`, with nested child types (`.../namespaces/{ns}/queues/{q}`, `.../databaseAccounts/{acct}/sqlDatabases/{db}/containers/{c}`) handled by the same generic path walker, not per-type route registrations.
- List forms: `GET .../resourceGroups/{rg}/providers/{ns}/{type}` and `GET /subscriptions/{sub}/providers/{ns}/{type}`.
- `POST .../{resourceId}/listKeys?api-version=...` — **not optional**: it is how azurerm obtains storage-account keys, Cosmos master keys, and Service Bus connection strings, and how any downstream data-plane resource gets its credentials.
- Every response body carries `id`, `name`, `type`, `location`, `tags`, and `properties.provisioningState: "Succeeded"`. Tags are modeled as a plain field on the resource, **not** the separate `Microsoft.Resources/tags/default` sub-resource — deferred.
- Error envelope: `{"error":{"code":"ResourceGroupNotFound","message":"..."}}` with the conventional status codes (404 missing, 400 malformed, 409 conflict), following `services/sqs`'s `errorDetails` table pattern.

**Resource-provider registration:** `GET /subscriptions/{sub}/providers`, `GET /subscriptions/{sub}/providers/{ns}`, `POST /subscriptions/{sub}/providers/{ns}/register`. Cheap to implement (the RP registry already knows its own types and API versions), and implementing it means the fixtures don't have to depend on `resource_provider_registrations = "none"` behaving as expected across provider versions.

**API-version handling:** parse and echo `api-version` — real ARM's own metadata endpoint is versioned `2022-09-01` specifically (confirmed against `go-azure-sdk`'s metadata client; do not serve `1.0`, which most public docs and Azure Stack examples show and which the real client does not request) — but **do not** branch response-body behavior on the caller's `api-version` value for other endpoints. One body shape per resource type, documented in `PARITY.md` as the version it was modeled against. Version-specific response shaping elsewhere is a deferred gap.

**Explicitly deferred (MVP):** management locks, Azure Policy, RBAC/`Microsoft.Authorization`, ARM template deployments (`Microsoft.Resources/deployments`), `PATCH` semantics beyond merge-into-existing, `$filter`/`$expand` on list operations, continuation-token paging (`nextLink`) on ARM lists, cross-subscription/cross-tenant, resource moves, `What-If`, and LRO polling (section 10.3).

### 10.2 One ARM service, not one per resource provider

**Recommendation: a single new service, `services/azurearm`, on one dedicated fixed port, dispatching internally by resource-provider namespace.** Three reasons, all grounded in this repo's own dispatch model:

1. Real Azure serves every RP from one host. `metadata_host` yields exactly one `resourceManager` URL, so splitting RPs across ports is not even expressible in the provider's configuration model — the emulation would have to lie about a shape the client can't consume.
2. `pkgs/service/priorities.go`'s priority ladder exists to disambiguate *AWS* services that share one listener by header/form shape. ARM's RPs don't need disambiguating by the `Router` at all: they're distinguished by a path segment (`/providers/Microsoft.Storage/...`) that a single handler parses once. Registering five matchers that all key off the same path prefix would be strictly worse than one handler with an internal `map[string]ResourceProvider` registry.
3. The per-service-fixed-port precedent from section 4 is about **data-plane** services whose wire protocols genuinely collide (`/<account>/<resource>` means three different things on 10000/10001/10002). ARM has no such collision — the collision would be *between ARM RPs*, which don't collide.

**Why a dedicated port rather than mounting ARM on the main AWS port (8000) via the shared `Router`.** Mounting it there is tempting — ARM's `/subscriptions/...`, `/metadata/endpoints`, and `/{tenant}/oauth2/token` paths are unambiguous against AWS's `X-Amz-Target`/form-POST shapes, and a versioned-path matcher at priority 85 would beat S3's priority-0 catch-all. Two things kill it: (a) an S3 bucket literally named `subscriptions` or `metadata` would be shadowed, a silent-wrong-answer failure mode the router's design otherwise avoids by construction; and (b) decisively, `metadata_host` is a bare hostname the provider prefixes with `https://` — ARM needs a TLS listener (section 10.8), while the main port is plain HTTP by default (`cli.go`'s `serveHTTP`/`tlsSettings` make TLS an all-or-nothing global opt-in). A dedicated ARM listener can be HTTPS-by-default without forcing every AWS SDK client in the process to switch schemes.

### 10.3 Async provisioning: always synchronous

**Decision: ARM always answers synchronously — `200 OK` on update, `201 Created` on create, `200`/`204` on delete, with `provisioningState: "Succeeded"` in the body from the first response. No `Azure-AsyncOperation` header, no `Location` header, no `/providers/Microsoft.X/locations/{loc}/operationResults/{id}` poll endpoints.**

The rationale is that there is nothing to emulate: real ARM returns 202 because provisioning a storage account takes 30 seconds of real work, and gopherstack's take microseconds. `azurerm`'s LRO handling (`hashicorp/go-azure-sdk`'s pollers) treats a terminal 200/201 with `provisioningState: Succeeded` as immediate completion and never polls, which is the whole point.

**The deferred gap, stated honestly** (same register as M0's multipart deferral): a client that *specifically exercises* LRO behavior — an SDK conformance test asserting a 202 and a poll URL, or user code that captures the poller and resumes it from a serialized token — will not find that behavior here. If that ever matters, the fix is additive and bounded: an opt-in `--azure-arm-async-lro` flag that returns 202 + `Azure-AsyncOperation` and completes the operation on first poll. Not MVP.

### 10.4 How ARM-created resources connect to the running data planes (the central design fork)

**Decision: ARM is a control-plane façade that owns ARM-shaped metadata only, and delegates every resource with a real data-plane meaning into the already-running service backend via in-process adapters wired in `cli.go` — exactly the pattern `wireCrossServiceDependencies` already uses ~60 times for AWS** (`wireSSMKMS`, `wireSNSToSQS`, `wireS3Notifications`; adapter structs in `cli_adapters.go`, narrow consumer-defined interfaces so `services/azurearm` never imports the data-plane packages). Concretely, per RP:

- **`Microsoft.Storage/storageAccounts`** — ARM stores the account resource (id/name/location/sku/kind/tags) and returns `properties.primaryEndpoints.{blob,queue,table}` plus `listKeys` returning `key1`/`key2` set to Azurite's `devstoreaccount1` key (`pkgs/azureauth.DefaultAccountName`/key). **No data-plane delegation is needed for the MVP**, because Blob/Queue/Table are *already* account-name-agnostic: `services/azureblob/handler.go`'s `splitPath` returns the account segment and every call site discards it (`_, container, blob := splitPath(...)`), and `services/azuretable`/`azurequeue` do the same. So an ARM-created account named `tfstorage123` is immediately usable at `http://host:10000/tfstorage123/...` today, with zero data-plane changes. The honest limitation, and the first `PARITY.md` known gap: **all ARM storage accounts alias one shared container/queue/table namespace** — two accounts see each other's containers. The follow-on (deferred, M11) is to key each storage backend's top-level map by account name and have the Storage RP call a `RegisterAccount(name)`/`DeleteAccount(name)` adapter, which also lets the data plane 404 an unknown account instead of silently creating state under it.
- **`Microsoft.ServiceBus/namespaces` + `/queues` + `/topics` + `/topics/{t}/subscriptions`** — this one *must* delegate, because the entire value of `azurerm_servicebus_queue` is that the queue is then sendable. The RP adapter calls `services/azureservicebus`'s `StorageBackend` create/delete methods, translating ARM's JSON `properties` (`lockDuration`, `maxDeliveryCount`, `defaultMessageTimeToLive` as ISO-8601 durations) into the existing `EntityConfig` struct (`services/azureservicebus/interfaces.go`) that M5's Atom+XML path already populates. The namespace resource itself stays metadata-only, mapped onto the fixed `DefaultNamespace = "sbemulatorns"` identity (`services/azureservicebus/sas.go`), with `.../AuthorizationRules/RootManageSharedAccessKey/listKeys` returning the connection string built from that fixed SAS key. Multi-namespace isolation is the same deferred gap as multi-account storage.
- **`Microsoft.DocumentDB/databaseAccounts` + `/sqlDatabases` + `/sqlDatabases/{db}/containers`** — the account resource is metadata-only and advertises `properties.documentEndpoint` pointing at the Cosmos Gateway (port 8081), with `listKeys` returning `DefaultMasterKey` (`services/cosmosdb/settings.go`). `sqlDatabases`/`containers` delegate into `services/cosmosdb`'s `StorageBackend` — including the partition-key path from ARM's `properties.resource.partitionKey.paths[0]`, which maps directly onto the single-path partition key M3 already implements — so a container created by `terraform apply` is immediately writable through the Gateway API and, per M6, through the Table API sharing that port.
- **Forward-compat for M13/M14** — `Microsoft.KeyVault/vaults` and `Microsoft.AppConfiguration/configurationStores` slot in as two more `ResourceProvider` implementations whose adapters register a vault/store name with the corresponding data-plane service and whose `listKeys`/`ListKeyValue` equivalents hand back the fixed dev credentials. Nothing in the ARM core changes.

**The endpoint-advertisement problem, and why it's the sharpest edge here.** `services/cosmosdb/account_ops.go` learned this the hard way: advertising `h.Port` instead of echoing the request's own `Host` makes SDKs "discover" a port nothing is listening on. ARM has the same problem *and can't use the same trick* — it must advertise **other services'** externally-visible host:port (Blob 10000, Queue 10001, Table 10002, Service Bus 10003, Cosmos 8081), which under a testcontainers-style ephemeral port mapping are not derivable from ARM's own `Host`. Resolution: (a) default each advertised endpoint to `scheme://<ARM request Host's hostname>:<that service's configured port>`, which is correct for `docker run -p 10000:10000 ...` and for a bare local binary; (b) add explicit overrides — `--azure-arm-advertise-blob-endpoint` and siblings, plus `AZURE_ARM_ADVERTISE_*` env vars — for remapped deployments; (c) have the Azure Terraform suite publish fixed host ports rather than ephemeral ones (section 10.8) so (a) is always right in CI. This must be designed in from the first commit; retrofitting it is how you get the failure mode `account_ops.go`'s comment warns about.

### 10.5 Auth strategy

Real ARM wants `Authorization: Bearer <JWT>` from AAD's client-credentials flow. gopherstack has no AAD, and `pkgs/azureauth` is SharedKey-only — a different scheme entirely. The precedent is `services/cognitoidp/tokens.go`, which already solves "issue structurally-valid OAuth2/JWT tokens without real cryptographic trust" (an RS256 `tokenIssuer`, deterministic key ID, `JWKS()`, `SigningCertificatePEM()`, `ParseAccessToken`, on `github.com/golang-jwt/jwt/v5`, already a direct dependency).

**Decision: extract a new shared package, `pkgs/aadauth`, modeled on `services/cognitoidp/tokens.go` rather than importing it.** Cognito's `tokenIssuer` is unexported and coupled to `UserPoolClient`/`clientTokenSettings`, so it can't be reused as-is, and copying it into two future callers (ARM now, Key Vault at M13) is exactly the duplication that M6 resolved by extracting `pkgs/odatatable`. `pkgs/aadauth` owns: the RSA keypair + JWKS, `IssueClientCredentialsToken(tenant, clientID, audience)` producing AAD-shaped claims (`iss: https://<host>/<tenant>/v2.0`, `aud`, `appid`, `tid`, `oid`, `sub`, `exp`, `iat`, `nbf`, `ver: "2.0"`), the `/{tenant}/v2.0/.well-known/openid-configuration` and `/common/discovery/instance` document builders, and `Parse`/`Validate`. Whether Cognito is later refactored onto it is a separate, optional cleanup — do **not** bundle that into this milestone.

**Fixed dev credentials**, in the same spirit as `devstoreaccount1` and Cosmos's published emulator key, living in `services/azurearm/settings.go` and overridable via flags/env:

| Setting | Default | Flag / env |
|---|---|---|
| Tenant ID | `00000000-0000-0000-0000-000000000000` | `--azure-arm-tenant-id` / `AZURE_ARM_TENANT_ID` |
| Subscription ID | `00000000-0000-0000-0000-000000000000` | `--azure-arm-subscription-id` |
| Client ID | `00000000-0000-0000-0000-000000000000` | `--azure-arm-client-id` |
| Client secret | `gopherstack` | `--azure-arm-client-secret` |
| Environment name | `gopherstack` | `--azure-arm-environment` |
| Default location | `local` | `--azure-arm-location` |

The all-zeros GUIDs match LocalStack's own Azure emulator convention and are valid GUIDs, which matters because azurerm parses `subscription_id`/`tenant_id` as GUIDs. **Validation is off by default**: the token endpoint issues a token for *any* `client_id`/`client_secret`, and ARM accepts any structurally-valid `Authorization: Bearer` header (and, for maximum tolerance in the MVP, a missing one) — with `--azure-arm-validate-tokens` opting into real signature+audience+expiry verification, mirroring `--cosmosdb-validate-auth`, `--azure-servicebus-validate-sas`, and `services/s3`'s `WithPresignValidation`.

### 10.7 Port reservation

Own fixed port, `DefaultPort = 10006` (`--azure-arm-port` / `AZURE_ARM_PORT`), synchronous bind in `StartWorker` with fail-fast and **no** `PortAlloc` fallback, exactly like Blob/Queue/Table/Service Bus (section 4) — the `net.ListenConfig.Listen` + dedicated `echo.New()` + `telemetry.WrapEchoHandler` shape in `services/azureblob/handler.go`'s `StartWorker`, with a matching `Shutdown`. `10006` leaves Key Vault (10004, now M13) and App Configuration (10005, now M14) untouched rather than renumbering ports that are cited elsewhere. It sits inside `--port-range-start`/`--port-range-end`'s default 10000-10100 range, so it needs the same `alloc.Reserve(cli.AzureARM.Port, "azurearm")` call in `cli.go`'s `reserveFixedServicePorts` as its siblings. `Dockerfile`/`Dockerfile.goreleaser`'s `EXPOSE 10000 10001 10002 10003 8081` line gains `10006`. Registration goes in `getMostRecentServiceProviders()` next to `&azureservicebusbackend.Provider{}`/`&cosmosdbbackend.Provider{}`, with `RouteMatcher()` returning a constant `false` and `MatchPriority()` 0, per the documented inert-matcher convention in `services/cosmosdb/provider.go`.

### 10.8 Terraform provider configuration, and the two things to verify first

The target provider block, modeled on LocalStack's own Azure emulator configuration:

```hcl
provider "azurerm" {
  features {}
  metadata_host                   = "localhost:10006"   # no scheme; provider prefixes https://
  environment                     = "gopherstack"        # must equal metadata doc's `name`
  subscription_id                 = "00000000-0000-0000-0000-000000000000"
  tenant_id                       = "00000000-0000-0000-0000-000000000000"
  client_id                       = "00000000-0000-0000-0000-000000000000"
  client_secret                   = "gopherstack"
  resource_provider_registrations = "none"   # azurerm 4.x; 3.x: skip_provider_registration = true
  storage_use_azuread             = false
}
```

The mechanism is that azurerm does **not** hardcode Azure's endpoints: at init it fetches `https://{metadata_host}/metadata/endpoints?api-version=2022-09-01` and builds every subsequent URL — token endpoint, resource manager, Key Vault DNS suffix, storage suffix — from that document. That is the single lever that redirects the entire provider, and it is why the metadata document is the first thing to implement.

**Found in M8, fixed: the metadata document is a single JSON object, not the array real Azure's public endpoint returns.** Real Azure's public `/metadata/endpoints` genuinely does return a JSON array (the multi-cloud discovery list — public/US Gov/China/etc.), and that public shape is what most docs, examples, and a plain reading of "GET /metadata/**endpoints**" (plural) suggest — which is exactly what M7 shipped (`BuildMetadataEndpoints` returned `[]EnvironmentDescriptor`). But the `metadata_host` custom-environment code path `terraform-provider-azurerm` actually uses never touches that public endpoint or its array-shaped client: `environments.FromEndpoint` calls `hashicorp/go-azure-sdk`'s `sdk/internal/metadata/client.go` `GetMetaData`, which does `json.Unmarshal(respBody, &metadata)` into a single `*metaDataResponse` struct and hard-fails on an array with `json: cannot unmarshal array into Go value of type metadata.metaDataResponse`. This went undetected through the whole of M7 and the first pass of M8 because no `terraform apply` had ever actually reached this endpoint before M8's CI-discovery-glob fix (`.github/workflows/ci.yml` never matched `test/terraform/azure/*_test.go`) let the Azure Terraform suite run in CI for the first time — CI on Linux got past the TLS-trust step that blocks local macOS runs and hit this immediately. Fixed by changing `BuildMetadataEndpoints`'s return type to a single `EnvironmentDescriptor` (`services/azurearm/metadata.go`) and updating every test that had encoded the array assumption (`TestBuildMetadataEndpoints`, `TestBuildMetadataEndpoints_CustomEnvironmentName`, `TestBuildMetadataEndpoints_IPv6Host`, `TestHandler_MetadataEndpoints`) to assert the object shape explicitly instead of indexing into `docs[0]` — those tests had all passed against a shape the real consumer rejects, which is the actual lesson here. **Do not revert this back to an array**: it matches real Azure's own public discovery document, which makes it an easy "fix" to reach for, but it is wrong for the one code path this emulator actually needs to satisfy.

**Resolved: TLS on the metadata host is mandatory, not merely likely.** Verified directly against `hashicorp/terraform-provider-azurerm`'s source (`internal/provider/provider.go`): when `metadata_host` is set, the provider calls `environments.FromEndpoint(ctx, fmt.Sprintf("https://%s", metadataHost))` — the `https://` scheme is hardcoded into the format string, and `metadata_host`'s own schema description confirms it's documented as a bare hostname (env var `ARM_METADATA_HOSTNAME`), so there is no configuration value that produces a plain-HTTP request. `hashicorp/go-azure-sdk`'s metadata client (`sdk/internal/metadata/client.go`) confirms this at the transport level: it builds the metadata URL by string-concatenating onto whatever scheme it was given, using a `tls.Config{MinVersion: tls.VersionTLS12}` with no `InsecureSkipVerify` and the default system trust store — so a self-signed cert must be trusted by whatever process runs `terraform`/`tofu`, not merely served. One real user (`terraform-provider-azurerm` issue #15743) confirms this from the outside: getting a custom `metadata_host` working required "add[ing] the self signed certificate ... to the trusted certificates on your local machine, or else terraform will complain about not trusting it."

One useful relaxation this resolution surfaces: `FromEndpoint` reads `resourceManager` out of the returned JSON and passes it to `ResourceManagerAPI(...)` **verbatim, with no scheme validation** — so while the *metadata document itself* must be served over trusted HTTPS, the `resourceManager` URL it points to (i.e., ARM's actual request/response traffic) can validly be `http://host:10006/`. The MVP should still serve the whole `services/azurearm` listener over HTTPS for simplicity and future-proofing (a plain-HTTP resourceManager is an unnecessary asymmetry to maintain), but it is not a load-bearing requirement the way the metadata document's HTTPS is.

**Build plan given this**: extract `cli.go`'s existing `generateSelfSignedCert` into a shared `pkgs/devtls` (it already exists for the main port's optional TLS mode, so this is a lift-and-share, not new crypto code), serve `services/azurearm` over HTTPS with a cert covering `localhost`/`127.0.0.1`/the container's DNS name, and have the Terraform test harness (`test/terraform/azure/`) trust that cert for the `tofu` child process — via `SSL_CERT_FILE` in `applyTofu`'s `env` slice on Linux/CI, with a documented fallback (install into the login keychain, or run the suite in a Linux container) if `SSL_CERT_FILE` doesn't get picked up by Go's darwin verifier; this is worth a five-minute check at implementation time but is no longer a design-blocking unknown; also model the metadata document against the real `2022-09-01` schema fields (`authentication`, `resourceManager`, `graphAudience`/`graph`, `suffixes`), since `FromEndpoint` hard-fails on missing `name`, `resourceManagerEndpoint`, and `microsoftGraphResourceId` — the last of which is easy to miss because most public "custom cloud" examples predate the schema version that requires it, and easy to get *wrong even when present*: it is a **top-level** field (`json:"microsoftGraphResourceId"` directly on the document root), not nested under a `resourceIdentifiers` object the way `hashicorp/go-azure-sdk`'s own *exported* `MetaData`/`ResourceIdentifiers` types (a separate, post-parse convenience shape) might suggest by name — the actual wire-level unexported `metaDataResponse` struct (`sdk/internal/metadata/client.go`) has no such nesting. Nesting it silently zero-values the field on unmarshal, so `FromEndpoint` fails with "no `microsoftGraphResourceId` was returned" rather than a JSON error, which is why this survived one full CI run of M8's own metadata reshape fix before being caught.

**Resolved: azurerm's *direct data-plane* resources (`azurerm_storage_container`/`_blob`/`_queue`/`_table`) can be redirected, and don't need any suffix trickery.** (`azurerm_storage_share`/`_file`, Azure Files, stay out of scope -- gopherstack has no File Share service to back them, unrelated to this finding.) This was flagged as the plan's single biggest open risk before M7 shipped; verified directly against the provider's source once M7's `properties.primaryEndpoints` shape existed to check it against. `terraform-provider-azurerm`'s storage data-plane clients (`internal/services/storage/client/data_plane.go`'s `ContainersDataPlaneClient`/`QueuesDataPlaneClient`/etc.) call `account.DataPlaneEndpoint(EndpointTypeBlob|Queue|Table)`, which (`client/helpers.go`) returns `ad.primaryBlobEndpoint`/`primaryQueueEndpoint`/`primaryTableEndpoint` -- fields populated straight from the ARM `GetProperties`/`Create` response body's `properties.primaryEndpoints.*`, i.e. exactly the values M7's `rp_storage.go` `buildBody` already returns (`http://<host>:10000/<account>/`, `:10001/`, `:10002/`). The `{account}.{suffixes.storage}` virtual-host construction is only a *fallback* (`client/helpers.go`'s `if baseUri == nil`) for when ARM didn't return a primary endpoint at all -- never our case. The client library underneath (`hashicorp/go-azure-sdk`'s `sdk/client/dataplane/storage`) makes this explicit in its own source comment: `NewStorageClient` "require[s] the baseUri is provided" because "both the domain name _and_ the domain format can change entirely" -- it never reconstructs or validates the host, it just uses whatever URI ARM handed back. **Net effect: no new gopherstack code is required in `services/azureblob`/`azurequeue`/`azuretable` at all** -- M0-M2's existing path-style listeners are already exactly what these clients expect once ARM (M7) is advertising them. The only remaining work is Terraform fixtures/tests proving it (see M8 below); this is why M8 is scoped as a small, mechanical milestone rather than another RP.

For everything ARM-mediated — resource groups, storage accounts, Service Bus namespaces/queues/topics/subscriptions, Cosmos accounts/databases/containers, and later Key Vault vaults and App Configuration stores — no such uncertainty exists: those are pure ARM calls and the metadata document fully controls where they go.

### 10.9 State, persistence, and reset

`services/azurearm/store.go` owns an `InMemoryBackend` holding the ARM resource graph: one subscription, resource groups, and a flat `map[normalizedResourceID]*Resource{ID, Name, Type, Location, Tags, Properties, SKU, Kind}`. `persistence.go` follows the established versioned-snapshot shape (`armSnapshot{Version: 1, ...}`, restored on boot, guarded against shape drift) as in `services/azureblob/persistence.go`.

**Restore must be idempotent against the data plane.** Each data-plane service snapshots and restores its *own* entities independently, so on restore ARM must not re-create a Service Bus queue that `services/azureservicebus`'s own snapshot already brought back. The adapters are therefore create-if-absent, and ARM's snapshot stores only ARM-side metadata (IDs, tags, ARM-only `properties`) — never a second copy of data-plane state. `Reset()` (`service.Resettable`) clears the ARM graph only, on the same reasoning: the `/_gopherstack/reset` endpoint already calls `Reset()` on every service, so the data planes clear themselves.
