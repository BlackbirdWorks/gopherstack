## Password sign-in

grant_type=password at the ARM token endpoint verifies a user's passwordProfile password (kept only as a salted PBKDF2-SHA256 hash, 120000 iterations, in the persisted secrets map; compared in constant time) and issues a token whose oid is the user. Errors follow the AADSTS codes of learn.microsoft.com/entra/identity-platform/reference-error-codes: 50126 invalid username or password, 50034 unknown user, 50057 disabled account, 50055 password change required, 50053 locked, 900144 missing username or password. Ten consecutive failures lock the account for one minute on the backend clock (learn.microsoft.com/entra/identity/authentication/howto-password-smart-lockout defaults); lockout state is in memory and is not persisted. Users restored from a snapshot without a stored hash fail with 50126 and a message naming PATCH /users/{id} passwordProfile.

## Emulator choices where the vendor is silent

- Custom role definitions: Learn gives no error for deleting a role that still has assignments, for a duplicate displayName or templateId, or for an unknown resource action; the emulator answers 400 Request_BadRequest for each, accepts any action shaped microsoft.<namespace>/<path>, and caps a tenant at 1000 custom roles, 100 permissions and 3000 actions.
- Devices: the Learn device page says alternativeSecurityIds, physicalIds and similar are internal use only and gives no uniqueness error, device count limit or registeredOwners type rule; the emulator answers 400 for a duplicate deviceId, caps devices at 5000 and links per device at 100, and accepts only users as registered owners and users.
- Delta: Learn names syncStateNotFound only as an example 40X code and describes no page-size control; the emulator uses a fixed page of 100, 410 for unknown or expired tokens and does not keep tokens across a restart (a restored backend answers 410, which clients treat as a restart).
- keyCredentials PATCH accepts at most 100 entries and rejects duplicate keyIds; Learn publishes neither.

- User responses return unset default properties as explicit nulls and the create-response carries the default property set; the Get user reference documents neither (its example response only shows populated properties).
- Disabling an app role that is still assigned is not refused; appRoles removal is not blocked while in use. learn.microsoft.com/en-us/graph/api/application-update documents only that isEnabled false is accepted in a PATCH of appRoles and says nothing about assigned roles, so the in-use rule is undocumented.
- Soft delete: group restore conflicts are not published (checked directory-deleteditems-restore and directory-deleteditems-list); the bare GET /directory/deletedItems without a type cast is an emulator extra, the list reference documents only the type-cast URLs.
- Error message texts are emulator choices: graph/errors, json-batching, application-post-federatedidentitycredentials and user-post-users give status classes only, so the texts for malformed ids ('Invalid object identifier'), duplicate identifierUris/uniqueName/UPN/servicePrincipalNames, unknown property, password complexity, appRoleAssignment validation, group creation rules (mail-enabled and neither-flag refusals, isAssignableToRole), the 405 error code, 'Unable to read JSON request payload', the federated-credential 409 code, the addKey proof failure, the $batch limit message, role assignment validation and the AADSTS assertion-failure texts are the emulator's.
- Only Microsoft Graph (a subset of its roles: Application.Read[Write].All, Directory.Read[Write].All, User.Read[Write].All, Group.Read[Write].All, Mail.Send; and scopes User.Read, openid, profile, email, offline_access) is a built-in service principal. learn.microsoft.com/en-us/troubleshoot/entra/entra-id/governance/verify-first-party-apps-sign-in says first-party applications do not always result in a service principal in the tenant, and lists only four application IDs, so other first-party applications are created on first use (POST /servicePrincipals with the appId) rather than seeded.

## Role assignment expansion

$expand=principal on /roleManagement/directory/roleAssignments (list and get) returns the principal as a typed directory object, `principal` null when the principal no longer exists, and honours a nested $select: learn.microsoft.com/en-us/graph/api/rbacapplication-list-roleassignments documents principal as the expandable property and the example shows the @odata.type and id of a user. Any other expand name answers 400.
