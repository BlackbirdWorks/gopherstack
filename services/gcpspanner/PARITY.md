Database.encryption_info reports CUSTOMER_MANAGED_ENCRYPTION with the primary key version and an encryption_status of FAILED_PRECONDITION while a key is unusable (Spanner CMEK documentation, cloud.google.com/spanner/docs/cmek).

## Emulator choices where the vendor is silent

- The emulator runs every instance in its single emulator-config with one node, so node_count, processing_units, autoscaling_config and replica_compute_capacity are metadata; the data plane is one shared emulator process.
- Autoscaling never resizes an instance (no load signal): capacity starts at the minimum limit and stays within the limits on update. replica_compute_capacity lists one entry per read-write and read-only replica location, in the unit the instance was sized with. node_count and processing_units are rejected on update while autoscaling is on.
- Duplicate-name, missing-object and dependency codes of DDL folding (ALREADY_EXISTS, NOT_FOUND, FAILED_PRECONDITION) and the etag mismatch code (ABORTED) of config and partition updates are not documented; instance-config create/update/delete and instance moves complete inside the call instead of passing through CREATING.
- List*Operations filters accept `AND`, `OR`, `NOT`, parentheses and the operators of the field docs; OR binds tighter than AND as in the instance filter, and the filter is capped at 4096 bytes, 256 tokens and 32 levels.
- Table data persistence reads each database through one read-only transaction when a snapshot is taken and replays it with InsertOrUpdate mutations, parents before interleaved children, skipping generated columns. At most 200000 rows, 64 MiB and 1000 tables per snapshot; the row and size bounds are enforced while the table is read (row limit on the read, receive-size cap on the response), and a database over a limit is persisted schema-only without using up the budget of later databases. Replay retries tables rejected for a foreign key until a pass makes no progress, commits at most 20000 cells and 8 MiB per transaction (the real mutation limit counts index entries too; the 1.5.40 emulator does not enforce it), and a database whose replay fails is emptied again and logged, never left half-restored. Tables in named schemas are not persisted. Sequence counters and change stream records are not persisted.
- Offline DDL folding stores any CREATE or DROP statement of a kind it does not model (SCHEMA and LOCALITY GROUP are tracked by name, PROTO BUNDLE as a singleton) and never rejects valid DDL it does not understand; ALTER actions it does not model (see items_still_open) are kept as separate statements that are removed together with the object they alter. PostgreSQL names accept the public schema prefix. A failing batch reports commit_timestamps only for the statements applied before it. The 1.5.40 emulator validates a whole UpdateDatabaseDdl batch up front and fails the call itself rather than the operation.
- The DDL reference pages and the fine-grained access control page give no printed form for GetDatabaseDdl, so the folded schema is printed as follows: a modified CREATE TABLE is re-rendered with one body item per line, OPTIONS clauses as `OPTIONS (key = value)`, trailing clauses in the CREATE TABLE grammar order (PRIMARY KEY, INTERLEAVE, ROW DELETION POLICY, OPTIONS); GRANT statements are merged into one statement per role and object with privileges ordered SELECT, INSERT, UPDATE, DELETE, EXECUTE, USAGE, role grants into one per grantee, and ALTER DATABASE options into one statement after the other statements. REVOKE of a privilege removes it, a column-level REVOKE does nothing to a table-level privilege (stated in the PostgreSQL DDL reference), DROP ROLE and DROP of a granted object remove the grants that name them, and RENAME TO rewrites the table name in indexes, interleave parents, foreign keys, change streams and grants but leaves view queries as written; the pages say nothing about prerequisites of DROP ROLE or about references after a rename. DROP DEFAULT on a column without a default and REVOKE of a privilege never granted are no-ops.
- Backups are held by the backend, not the emulator (the gcr.io/cloud-spanner-emulator/emulator:1.5.40 image answers CreateBackup and RestoreDatabase with a message-less UNIMPLEMENTED): a backup keeps the DDL current at the request and the rows read at version_time, so a schema change between version_time and the request is not undone; size_bytes is the byte size of that DDL and of the encoded rows, with freeable and exclusive size equal to it; backups are not incremental; expired backups are not deleted automatically; DeleteInstance removes the instance backups with it; the optimize operation of a restore finishes immediately; backup creation runs in the background and an operation or backup caught mid-creation by a snapshot is dropped and its operation aborted. The Cloud Spanner documentation gives no limits for the emulator backup storage, so 100 backups per instance and 256 MiB per backend are the emulator own.
- Finished long-running operations are kept for 7 days and at most 10000 per backend (the oldest go first, unfinished ones never); the Cloud Spanner documentation gives no retention for them.
- kms_key_names on a multi-region config must name exactly one key per replica location (the use-cmek page shows one regional key per replica location); the page documents no error code, INVALID_ARGUMENT is used.
- Backend instance and database create_time values are the backend's own and are not shared with the emulator.
