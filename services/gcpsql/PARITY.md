## Emulator choices where the vendor is silent

- Duplicate database and user inserts return 409; the real reason strings were not verified against the live service. The earliest-recovery bound text and the error strings for a replica without binary logging and a non-replica promote are not documented (the manage-replicas and pitr pages quote none).
- Docker engines need the container runtime to see the emulator's temp directory (bind mount), so a gopherstack inside a container that talks to a remote daemon cannot export, import, back up or clone; admin SQL still works.
- MySQL PITR resolution is one second and replays over replication, so the source engine must be running; PostgreSQL clones need the WAL archive volume, and a PostgreSQL recovery to a time before any commit following the base fails at the engine, not at the API.
- Password policy (settings.passwordValidationPolicy, fields per the sqladmin v1 discovery document) is enforced on user insert and update when enablePasswordPolicy is true: minLength, COMPLEXITY_DEFAULT (lowercase, uppercase, digit and other character all present), disallowUsernameSubstring (case-insensitive), reuseInterval (last N passwords, kept as salted-by-user SHA-256 hashes, at most 100) and passwordChangeInterval (PostgreSQL only). The docs name the options but not the error text or status; violations are 400 "Password validation failed: ...". The policy is not applied to the instance root password.
- Automated backups run for primaries with backupConfiguration.enabled, once per UTC day, starting at backupConfiguration.startTime (the real service starts them anywhere in a four-hour window), checked every minute; automated backups beyond backupRetentionSettings.retainedBackups (default 7, COUNT unit only) are deleted oldest first, on-demand backups never are. A failed automated run is not retried that day.
- With storageAutoResize on, dataDiskSizeGb is raised to the next whole GiB above the data size (capped by storageAutoResizeLimit) when the poll sees the data outgrow it; the real increment is not documented. settingsVersion is not bumped.
- Replicas may be in any region of the primary's project; a DR replica (replicationCluster.failoverDrReplicaName) can be in any region. Cross-project replicas are rejected.
- maintenanceWindow and denyMaintenancePeriods are stored; maintenance events are Google-scheduled, so none is ever created.

- executeSql reports a database error as status code 3 with the engine's message and no results; the column type is the engine's own type name in upper case (INT4, VARCHAR); a statement without rows reports the PostgreSQL command tag or "Query OK, N rows affected" for MySQL; a missing dataApiAccess is a 403 with the documented message.
- executeSql with an omitted user runs as the built-in administrator; with a user and no passwordSecretVersion it uses the password stored for that account.
- A REGIONAL instance runs its standby as a hidden replica engine on a second data volume slot; after a failover the promoted engine keeps the data in its slot (persisted as slot) and the old primary's volumes are deleted.
- Clients connect through a per-instance front door on 127.0.0.1 that forwards to the current engine and applies authorizedNetworks live; every peer is a loopback address, so only 127.0.0.0/8 entries distinguish peers, an empty list admits everyone (real instances admit nobody without the Auth Proxy), and ipv4Enabled false admits nobody. The engine's own published port is not filtered.
- Disk-full mode is polled every 5 seconds against logical data size (PostgreSQL sets default_transaction_read_only, which a session can override; MySQL sets super_read_only). A smaller dataDiskSizeGb is a 400.
- A replica hierarchy is at most four levels deep including the primary (cloud.google.com/sql/docs/mysql/replication and /postgres/replication); records and data flow through intermediate replicas. Switchover needs a replica of a primary, not of another replica. A DR replica is designated with replicationCluster.failoverDrReplicaName on the primary.
